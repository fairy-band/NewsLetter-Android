기존 기능 하나를 개선하거나 수정한다. 요청 내용: `$ARGUMENTS`

`$ARGUMENTS`가 비어 있으면 무엇을 바꾸고 싶은지 묻고 시작한다.

## 범위

| 구분 | 정의 | 예 |
|------|------|----|
| 개선 | 기존 동작을 그대로 유지하면서 추가·확장·최적화 | 필터 옵션 추가, 목록 로딩 속도 개선, 공유 대상 추가 |
| 수정 | 의도대로 동작하던 기존 동작·인터페이스·기본값을 변경하거나 제거 | 알림 기본값 끔→켬, 정렬 기준 변경, 탭 제거 |

**버그 수정과 리팩터링은 다루지 않는다.** 요청이 이쪽이면 "이 요청은 /change 대상이 아니에요. 버그 수정·리팩터링은 `/plan`으로 계획서를 먼저 만든 뒤 진행해 주세요."라고 안내하고 종료한다.
완전히 새로운 기능(새 화면, 새 도메인)이면 `/feature`를 안내한다.

## 1단계: 요구사항 정리

요청을 아래 세 줄로 짧게 정리해 보여준다.

- **목표**: 무엇을 왜 바꾸는가
- **성공 기준**: 변경 후 화면이나 테스트에서 관찰 가능한 결과. "잘 동작한다" 같은 표현은 쓰지 않는다
- **범위**: 포함 / 제외

목표나 성공 기준을 코드와 요청만으로 정할 수 없으면 질문한다. 코드베이스 관례로 합리적으로 정할 수 있는 것은 묻지 말고 정리에 "결정 사항"으로 적는다.

## 2단계: 구조 파악

`CLAUDE.md`의 아키텍처를 기준으로 다음을 확인한다.

- 관련 코드: 변경 대상 Screen / ViewModel / UseCase / Repository / Service / DataStore
- 호출 지점: 변경 대상을 쓰는 곳 전부 (Grep으로 확인. 딥링크, Remote Config 키, FCM 페이로드, 서버 API 필드처럼 코드 밖에서 참조하는 것도 포함)
- 기존 테스트: 변경 대상을 검증하는 테스트와 그 테스트가 기대하는 동작

탐색 범위가 여러 모듈에 걸쳐 출력이 많아질 것 같으면 Explore 서브에이전트에 맡기고 결론만 받는다.

### 버그 여부 확인

현재 동작이 의도와 다르면 그건 기능 변경이 아니라 버그다. 버그 위에 기능을 얹으면 버그가 기능 변경 안에 묻혀 리뷰와 이력 추적이 어려워지므로, 여기서 **중단**하고 알린다.

의도는 기존 테스트의 기대값, 이슈·PR·커밋 메시지, 코드 주석, UI 문구에서 판단한다. 예를 들어 테스트는 7개를 기대하는데 코드는 6개를 반환한다면 버그다.
중단할 때는 어떤 근거로 버그라고 봤는지(기대 동작 vs 실제 동작, 관련 파일·줄)를 보여주고 `/plan`으로 버그 수정을 먼저 진행하도록 안내한다.
의도를 판단할 근거가 부족하면 개발자에게 현재 동작이 의도된 것인지 묻는다.

## 3단계: 유형 판정

기존 사용자·호출자가 관찰하던 동작이 하나라도 바뀌면 **수정**, 아니면 **개선**이다.
판단 기준은 "변경 전에 통과하던 기존 테스트나 기존 사용 흐름이 그대로 유지되는가"다. 기본값 변경, 정렬·순서 변경, 파라미터 추가로 기존 호출 결과가 달라지는 경우도 수정이다.

판정 결과와 근거를 한두 줄로 보여준다.

### 개선이면

바로 4단계로 간다.

### 수정이면

아래를 정리해 보여주고 `이대로 진행할게요 (Y/n)`로 확인받는다. 빈 응답이나 `Y`/`y`는 승인, `n`이면 무엇을 바꿀지 묻고 반영해 다시 확인받는다.

- **바뀌는 동작**: 변경 전 → 변경 후
- **영향받는 사용처**: 2단계에서 찾은 호출 지점, 사용자 흐름, 외부 참조 (파일·줄 포함)
- **호환성 대책**: 사용처별로 어떻게 처리할지. 예:
  - DataStore 키·값 의미 변경 → 기존 저장값 마이그레이션 또는 기본값 처리
  - 서버 API 요청·응답 변경 → 서버와의 배포 순서, 구버전 앱 대응
  - 딥링크·공유 링크 변경 → 이미 배포된 링크 처리
  - Remote Config 키 변경 → 기존 키 유지 여부
  - 대책이 필요 없으면 왜 없는지 적는다
- **수정할 기존 테스트**: 기대 동작이 바뀌어서 고쳐야 하는 테스트와 이유

확인 없이 구현에 들어가지 않는다. 수정은 사용자가 체감하는 동작을 바꾸므로 개발자가 그 영향을 알고 동의해야 한다.

## 4단계: 구현

- 작은 단위로 나눠 진행한다. 한 단위를 마칠 때마다 빌드가 깨지지 않는 상태를 유지한다.
- **범위 밖 변경은 하지 않는다.** 근처 코드의 리팩터링, 이름 정리, 관련 없는 버그 수정은 하고 싶어도 하지 않고 완료 보고의 "발견 사항"에 적는다. 섞이면 리뷰어가 의도한 변경과 부수 변경을 구분할 수 없다.
- 성공 기준을 확인하는 유닛 테스트를 추가한다 (Kotest + JUnit 5, 기존 테스트 스타일을 따른다).
- 기존 테스트 수정은 3단계에서 정리한 것만 한다.
  - 개선인데 기존 테스트를 고쳐야 통과한다면 기존 동작이 바뀐 것이다. 멈추고 유형을 수정으로 다시 판정해 3단계 확인을 받는다.
  - 수정 중 계획에 없던 기존 테스트를 고쳐야 하면 멈추고 이유와 함께 확인받는다.
- 구현을 마치면 `./gradlew assembleDebug`와 변경 모듈의 `testDebugUnitTest`를 직접 돌려 명백한 컴파일 에러와 테스트 실패는 검증 전에 고친다.

## 5단계: 검증

`.claude/agents/verifier.md`가 없으면 변경 요약을 보여주고 "검증 에이전트(.claude/agents/verifier.md)를 만들어 주세요"라고 요청한 뒤 완료 보고로 넘어간다.

### 검증 문서 작성

verifier는 대화 기록을 모르고 파일에 적힌 시나리오만 보고 기기에서 검증한다. 그래서 검증에 필요한 내용을 `.claude/plans/change-<기능명>.md`에 정리한다. 기능명은 요청에서 만든 영문 kebab-case 2~4단어다 (예: `notification-default-on`).

```markdown
# change-<기능명>

## 요청
- <$ARGUMENTS 원문>

## 유형
- <개선 | 수정> — <판정 근거 한 줄>

## 변경 요약
- <무엇을 어떻게 바꿨는지>

## 성공 기준
- <1단계에서 정리한 성공 기준>

## 호환성 영향
- <수정이면 바뀌는 동작, 영향받는 사용처, 대책. 개선이면 "기존 동작 변경 없음">

## 수정한 기존 테스트
| 테스트 | 이유 |
|--------|------|
<없으면 "없음">

## 필요한 앱 권한
- <없으면 "없음">

## 검증 시나리오
### 1. <시나리오명>
- 진입 경로: <앱 실행 후 어떤 탭·버튼을 거쳐 어느 화면으로 가는지, 사전 조건 포함>
- 조작: <누를 요소의 화면 텍스트 또는 content-description, 입력값 등>
- 기대 결과: <화면에서 관찰 가능한 텍스트, 요소 상태, 전환될 화면>
```

검증 시나리오에는 성공 기준을 확인하는 시나리오와 함께, **기존 동작이 유지되는지 확인하는 시나리오**를 최소 하나 넣는다. 개선이면 기존 흐름이 그대로인지, 수정이면 영향받는 사용처 중 바뀌지 않아야 하는 부분이 그대로인지 확인한다.

### verifier 호출

Agent 도구로 `verifier` 서브에이전트를 호출한다. 프롬프트에 다음을 명시한다.

```
검증 유형: feature-change
plans 파일 경로: .claude/plans/change-<기능명>.md
기능명: <기능명>
변경 유형: <개선 | 수정>
변경 요약: <한두 줄>
성공 기준: <목록>
수정한 기존 테스트: <테스트와 이유, 없으면 "없음">
```

| 결과 | 처리 |
|------|------|
| 성공 | 완료 보고로 간다. |
| 부분 성공 | 미검증·의심 항목을 보여주고, 이대로 마칠지 구현으로 돌아갈지 묻는다. |
| 실패 | 보고의 원인을 바탕으로 고친 뒤 다시 호출한다. 수정 방향이 4단계의 "멈추고 확인받는 경우"에 해당하면 먼저 확인받는다. |
| 기기 대기 | 보고된 개발자 조치를 안내하고, 준비됐다고 하면 다시 호출한다. 실패 횟수에 세지 않는다. |

검증 실패가 **5회**에 도달하면 반복을 멈추고 회차별 실패 원인과 공통 원인, 개발자가 판단할 부분을 보고하고 종료한다. 같은 원인으로 계속 실패한다면 계획 자체를 다시 봐야 하는 신호다.

## 완료 보고

짧게 아래 형식으로 보고한다.

```markdown
## /change 완료

- 유형: <개선 | 수정>
- 변경 내용: <1~3줄>
- 호환성 영향: <수정이면 바뀐 동작과 대책 요약, 개선이면 "없음">
- 수정한 기존 테스트: <목록과 이유, 없으면 "없음">
- verifier 결과: <성공 | 부분 성공 | 실패 | 미실행> — <미검증·의심 항목 요약>
- 발견 사항: <범위 밖이라 손대지 않은 버그·리팩터링 후보, 없으면 생략>
```
