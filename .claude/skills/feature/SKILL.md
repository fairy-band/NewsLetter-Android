새 기능 하나를 계획부터 PR까지 진행한다. 입력: `$ARGUMENTS`

## 0단계: 입력 해석

### 이슈 번호와 기능 설명 확보

- **이슈 번호만 들어온 경우** (`123`, `#123`):
  `gh issue view <번호> --json number,title,body,labels`로 이슈를 읽어 제목과 본문을 기능 설명으로 쓴다.
  조회에 실패하면(이슈 없음, gh 인증 실패, 네트워크 등) 실패 사유를 알리고 개발자에게 기능 설명을 요청한다.
- **설명만 들어온 경우**: 개발자에게 이슈 번호를 묻는다.
- **둘 다 없는 경우**: 이슈 번호와 기능 설명을 함께 묻는다.

### 범위 판단

이 스킬은 **새 기능 구현**만 다룬다. 기능 구현에 필요한 기존 코드 변경은 허용한다.

- 요청이 버그 수정이나 리팩터링이면(이슈 라벨 `bug`/`fix`/`refactoring`, 또는 설명의 성격으로 판단)
  "이 요청은 새 기능이 아니라 /feature 스킬의 대상이 아니에요. 버그 수정·리팩터링은 `/plan`으로 계획서를 먼저 만든 뒤 진행해 주세요."라고 안내하고 종료한다.
- 기능 추가인지 개선·수정인지 애매하면 개발자에게 새 기능이 맞는지 확인한다.

### 기능명

기능 설명에서 영문 kebab-case 기능명을 만든다 (예: `bookmark-sync`, `article-share-link`). 2~4단어로 짧게 한다.

### 기존 작업 확인

`.claude/plans/feature-<이슈번호>-*.md`가 이미 있으면 개발자에게 묻는다.

- **이어서 진행**: 기존 plans 파일의 기능명을 그대로 쓴다. plans 파일과 `.claude/processes/feature-<이슈번호>-<기능명>.md`(있으면)를 읽고,
  브랜치·변경 사항·검증 기록을 보고 어느 단계부터 이어갈지 정해 개발자에게 알린 뒤 진행한다.
  검증 실패 횟수는 processes 파일의 회차 수부터 이어서 센다.
- **새로 시작**: 기존 plans·processes 파일을 덮어쓸지 확인받고 1단계부터 진행한다.

## 1단계: 탐색과 계획

### 1. 브랜치 생성

```bash
git status --porcelain
git fetch origin develop
git switch -c feature/<이슈번호>-<기능명> origin/develop
```

- 커밋되지 않은 변경이 있으면 브랜치를 바꾸기 전에 개발자에게 어떻게 할지(stash, 그대로 가져가기, 중단) 묻는다.
- 같은 이름의 브랜치가 이미 있으면 새로 만들지 않고 그 브랜치로 전환할지 묻는다.

### 2. 코드베이스 탐색

`CLAUDE.md`의 아키텍처·네이밍 컨벤션을 기준으로, 기능과 관련된 모듈, 기존 패턴(비슷한 화면의 ViewModel/State/Screen 구성, Repository·UseCase 구조, Koin 등록 방식), 재사용할 수 있는 코드와 컴포넌트를 파악한다.
여러 모듈을 넓게 훑어야 해서 탐색 출력이 많아질 것 같으면 Explore 서브에이전트에 맡기고 결론만 받아 메인 대화의 컨텍스트를 아낀다.

### 3. 빠진 정보 질문

구현 범위, 엣지 케이스 처리, 에러 처리, UI 문구·디자인 등 코드와 이슈만으로 정할 수 없는 부분이 있으면 개발자에게 질문한다.
코드베이스의 관례로 합리적으로 정할 수 있는 것은 묻지 말고 스킬이 결정하되, 그 결정은 4번 단계 확인 때 모두 보여준다.

### 4. 단계별 계획 확인

계획을 아래 다섯 단계로 나눠 **한 번에 한 단계씩** 요약을 보여주고 `이렇게 구현할게요 (Y/n)`로 확인받는다.
빈 응답이나 `Y`/`y`는 승인으로 본다. `n`이면 무엇을 바꿀지 묻고 반영한 뒤 그 단계를 다시 확인받는다.
각 단계 요약에는 스킬이 내부적으로 결정한 사항도 "결정 사항"으로 빠짐없이 적는다.

a. **구현 범위**: 포함 / 제외
b. **구조와 설계**: 변경·추가할 파일과 모듈, 데이터 흐름 (예: Screen → ViewModel → UseCase → Repository → Service/DataStore)
c. **엣지 케이스와 에러 처리**
d. **유닛 테스트 계획**: 대상 클래스와 테스트 케이스 (Kotest + JUnit 5)
e. **검증 시나리오**: 기기에서 수행할 시나리오와 미리 부여할 앱 권한

다음에 해당하는 항목이 있으면 해당 단계 요약에 `⚠️ 주의` 블록으로 따로 짚는다.

- DB·DataStore 스키마 변경 (키 추가·변경·삭제, 마이그레이션 필요 여부)
- 공개 API 변경 (서버 API 요청·응답, 딥링크 스킴, 다른 모듈이 쓰는 인터페이스)
- 새 의존성 (`gradle/libs.versions.toml` 추가·버전 변경)
- 기존 동작 변경 (사용자가 체감하는 기존 화면·흐름의 변화)

### 5. plans 파일 작성

확정된 내용을 `.claude/plans/feature-<이슈번호>-<기능명>.md`에 아래 구조로 작성한다.

```markdown
# feature-<이슈번호>-<기능명>

## 이슈
- 이슈: #<이슈번호>
- 기능 설명: <기능 설명>

## 구현 범위
### 포함
- ...
### 제외
- ...

## 설계
### 변경·추가 파일
| 모듈 | 파일 | 변경 내용 |
|------|------|----------|
### 데이터 흐름
- ...
### 주의 사항
- <스키마 / 공개 API / 새 의존성 / 기존 동작 변경. 없으면 "없음">

## 엣지 케이스와 처리 방법
| 상황 | 처리 |
|------|------|

## 개발자 질문과 답변
- Q: ... / A: ...

## 유닛 테스트 계획
| 대상 | 케이스 |
|------|--------|

## 필요한 앱 권한
- <검증 전에 미리 부여할 런타임 권한. 없으면 "없음">

## 검증 시나리오
### 1. <시나리오명>
- 진입 경로: <앱 실행 후 어떤 탭·버튼을 거쳐 어느 화면으로 가는지>
- 조작: <누를 요소의 화면 텍스트 또는 content-description, 입력값, 스크롤 등>
- 기대 결과: <화면에 보여야 할 텍스트, 요소 상태(selected/checked/enabled), 전환될 화면>
```

검증 시나리오는 verifier 에이전트가 **이 섹션만 보고** 기기에서 따라 할 수 있어야 한다.
버튼·탭은 화면에 보이는 텍스트나 content-description으로 지칭하고, 기대 결과는 화면에서 관찰 가능한 형태로 쓴다. "정상 동작한다" 같은 모호한 표현은 쓰지 않는다.
필요한 사전 조건(로그인 상태, 데이터가 있어야 함 등)도 진입 경로에 적는다.

## 2단계: 구현

- plans 파일대로 구현하고, 계획에 있는 유닛 테스트도 작성한다.
- 구현 중에는 개발자에게 질문하지 않는다. 단, 아래 경우는 멈추고 묻는다.
  - 계획의 전제가 틀렸다는 것을 발견했을 때
  - 계획에 없던 DB 스키마, 공개 API, 새 의존성, 기존 동작 변경이 필요할 때
  - 구현 범위를 바꿔야 할 때

  이 경우 개발자 답변을 반영해 plans 파일(해당 섹션과 "개발자 질문과 답변")도 함께 갱신한다.
- 빌드·테스트 명령은 `CLAUDE.md`를 따른다. 구현을 마치면 `./gradlew assembleDebug`와 변경 모듈의 `testDebugUnitTest`를 직접 돌려 명백한 컴파일 에러와 테스트 실패는 검증 전에 고친다.
- **커밋은 하지 않는다.** 커밋은 PR 단계에서 처리한다. 작업 중 커밋 여부를 묻는 훅이 떠도 이 스킬 진행 중에는 커밋을 제안하지 않는다.

## 3단계: 검증

`.claude/agents/verifier.md`가 없으면 구현 결과(변경 파일, 구현 내용, 작성한 테스트)를 요약하고
"검증 에이전트(.claude/agents/verifier.md)를 만들어 주세요"라고 요청한 뒤 종료한다.

있으면 Agent 도구로 `verifier` 서브에이전트를 호출한다. 서브에이전트는 대화 기록을 모르므로 프롬프트에 다음을 명시한다.

```
검증 유형: feature
plans 파일 경로: .claude/plans/feature-<이슈번호>-<기능명>.md
이슈 번호: <이슈번호>
기능명: <기능명>
```

verifier는 빌드 → 유닛 테스트 → 기기 테스트(기능 동작, UI 정상 출력) 순서로 검증하고 결과를 **성공 / 부분 성공 / 실패 / 기기 대기** 중 하나로 보고한다.

| 결과 | 처리 |
|------|------|
| 성공 | 4단계로 간다. |
| 부분 성공 | 미검증·의심 항목을 개발자에게 보여주고, PR 단계로 갈지 구현으로 돌아갈지 묻는다. |
| 실패 | 아래 [실패 처리]를 따른다. |
| 기기 대기 | 보고된 "개발자 조치"를 안내하고, 준비됐다고 하면 verifier를 다시 호출한다. 실패 횟수에 세지 않고 processes 파일에도 기록하지 않는다. |

## 실패 처리

`.claude/processes/feature-<이슈번호>-<기능명>.md`에 회차별로 누적 기록한다. 같은 이슈는 항상 같은 파일에 이어서 쓴다.

```markdown
## <회차>회차 — <YYYY-MM-DD HH:mm>

- 실패 단계: <빌드 | 유닛 테스트 | 기기 테스트>
- 핵심 에러: <verifier 보고의 실패 상세 요약, 관련 파일·줄>
- 추정 원인: <verifier 보고 기반>
- 새 계획: <무엇을 어떻게 고칠지>

<details><summary>verifier 보고 원문</summary>

<verifier 보고 전체>

</details>
```

- 시각은 `date "+%Y-%m-%d %H:%M"`으로 얻는다.
- 새 계획이 plans 파일 내용(설계, 엣지 케이스, 테스트 계획, 검증 시나리오 등)을 바꾸면 plans 파일도 갱신한다.
- 기록 후 개발자 확인 없이 2단계(구현)로 돌아가 새 계획대로 고치고 다시 3단계를 진행한다.
  단, 새 계획이 2단계의 "멈추고 묻는 경우"에 해당하면 개발자에게 확인받는다.
- **검증 실패가 5회에 도달하면 더 이상 반복하지 않는다.** processes 파일을 요약해 개발자에게 보고하고 종료한다. 보고에는 다음을 포함한다.
  - 회차별 실패 단계와 원인 한 줄 요약
  - 반복된 실패의 공통 원인
  - 개발자가 판단해야 할 부분 (계획 수정, 범위 축소, 환경 문제 확인 등)

## 4단계: PR

`.claude/agents/pr-creator.md`가 있으면 Agent 도구로 `pr-creator` 서브에이전트를 호출해 PR을 올린다. 프롬프트에 다음을 전달한다.

```
이슈 번호: <이슈번호>
기능명: <기능명>
plans 파일 경로: .claude/plans/feature-<이슈번호>-<기능명>.md
검증 결과: <성공 | 부분 성공(개발자 승인)> — <단계별 결과와 미검증·의심 항목 요약>
```

PR이 올라가면 PR URL을 개발자에게 알린다.

없으면 검증 결과를 요약하고 "PR 에이전트(.claude/agents/pr-creator.md)를 만들어 주세요"라고 요청한 뒤 종료한다.
